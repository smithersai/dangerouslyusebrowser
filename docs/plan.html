The browser remains a separately sandboxed process tree. Node does not host Chromium's UI loop or V8 runtime. A missing fork is an error; there is no fallback browser. The native protocol can grow with new fork seams.

Two assumptions the source disproved

A navigation interceptor does not cover the network

The original proposed header explicitly describes navigation requests. A network-service proxy covers ordinary network traffic, but service workers can return synthetic or cached responses without reaching it. The implementation needs those response paths too, plus an audit of memory-cache delivery. Tests distinguish each origin of a response.

Existing virtual time does not establish tab isolation

The current controller is tied to a thread scheduler; its coordinator installs a process-wide clock override. The planned fork needs page-owned timer domains, coherent performance/animation clocks, and context-aware V8 Date handling. The early spike must freeze one of two tabs sharing a renderer and prove the other still advances normally.

WebMCP discovery and invocation have lifecycles

At this source revision there is no WebMCP listTools command. Enabling the domain emits tool registration events. Invocation returns an ID before the tool response arrives. Dub needs a live, frame-aware catalog and completion/cancellation handling; returning an invocation ID is not tool completion.

One builder, exact receipts

Start with Linux x86-64, 128 GB RAM and at least 500 GB usable NVMe. One builder owns the source/output tree. Keep upstream source outside the Dub repository, pin Chromium and DEPS, apply checked overlays, and sync exact jj commits on main. Record build logs, toolchain, GN arguments, tests and artifact checksums together. Hardware quotes and server access stay private.

Do not forecast compile time as a measured result. Record the first clean and incremental builds on the purchased host. macOS binding success is separate from a macOS browser release.
